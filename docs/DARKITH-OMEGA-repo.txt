Repository: An Invariant Decomposition Across Eleven Attested Senses and Eight Technical Specifications

A terminological analysis

---

Abstract

The English lexeme repository is used across software engineering, library and information science, package management, and institutional data governance as if it were univocal. It is not. This paper argues that the term names a single functional invariant — an authoritative, bounded, persistent holding environment whose organizational apparatus is separate from its raw content and which mediates access through an internal logic of preservation, retrieval, modification, distribution, or versioned reconstruction — instantiated across eleven attested historical senses and eight technical specifications. The invariant is decomposed into four conditions (relational, structural, functional, authority); each is shown necessary and the four jointly sufficient, including a direct argument against the objection that the functional condition entails the relational one. Every enumeration is closed by explicit count and a stated membership rule. The paper states its novelty boundary (the invariant is a synthesis over public components) and four falsification conditions. It is offered as a contribution to terminology and to the analysis of informational and institutional systems.

Keywords: repository, terminology, invariant analysis, version control, digital preservation, domain-driven design

---

1. Introduction

Repository is used across software engineering, library and information science, package management, and institutional data governance with the working assumption that the term is univocal. It is not. A Git repository, an OCI registry, a domain-driven-design (DDD) Repository interface, a Fedora institutional repository, and a 1759 commercial repository share a name and a family resemblance but differ in what they preserve, how their apparatus is separated from their content, and what authority they carry.

This paper makes three claims and one non-claim. The claims: (1) the eleven attested senses of repository are re-instantiations of one functional invariant, not independent senses; (2) the eight technical specifications are distinct instantiations of the same invariant at different layers, not rival definitions; (3) the invariant decomposes into four conditions that are individually necessary and jointly sufficient. The non-claim: the invariant is not newly discovered. Its components are public; the synthesis is the contribution.

The paper follows a closure discipline throughout: every enumeration terminates by an explicit count and a stated membership rule; every substantive assertion is flagged resolved (derivation carried here), exposable (mechanism established in the cited source, verbatim quotation not carried), or inferred (author's synthesis). Section 9 states the falsification conditions under which the paper is wrong.

2. Etymology and the root sense

Latin repositorium derives from repositus, past participle of reponere (re- "back" + ponere "to place"). The root sense is "put back in its proper place." The prototype of the invariant is already present: a support structure separated from the thing supported, with a placement logic. The immediate chain is uncontested in standard etymological sources (Lewis & Short 1879, s.v. repositorium; Oxford English Dictionary 3rd ed. 2009, s.v. repository; Französisches Etymologisches Wörterbuch, s.v. repositorium). The deeper Proto-Indo-European root of ponere is not needed for the argument and is not asserted (exposable: the deeper root is hedged in the cited dictionaries and is not load-bearing here).

5. Structure: the four cores and the collapse question

5.1 The four conditions

· Core A — Relational. An authoritative, organized holding environment that persists objects over time or version and mediates access by an internal logic.
· Core B — Structural. Organizational apparatus separated from raw content.
· Core C — Functional. A preservation contract, a retrieval mechanism, and a purpose boundary, all three present.
· Core D — Authority. Server-of-record status; not a derived copy.

5.2 Failure modes

Core Statement Failure mode if absent
A Authoritative organized holding environment Bare container
B Apparatus separate from raw content Folder
C Preservation + retrieval + boundary Cache
D Server-of-record authority Mirror

The failure-mode labels are not stipulated definitions but names for what remains when a conjunct is removed. Their function is expository: they fix the intuition that a thing failing exactly one core is a recognizable kind of near-repository. The necessity proof in §5.3 does not depend on accepting the labels.

5.3 The collapse question, addressed directly

A reviewer may ask whether Core C entails Core A, which would collapse the four cores to three. It does not. The argument is as follows.

Core C consists of three properties: (i) a preservation contract, (ii) a retrieval mechanism, (iii) a purpose boundary. Core A consists of one property: an authoritative, organized holding environment that persists objects and mediates access. Consider a system that satisfies (i)–(iii) without A. A write-once backup archive with a documented retention policy (preservation contract), a catalog (retrieval mechanism), and a scope statement (purpose boundary) satisfies all three C properties. But if the archive's holdings are derivative copies of another system's holdings — that is, if it lacks server-of-record status — it fails A (and also D). A second example: a read-through cache with a TTL retention policy, a lookup key, and a configured namespace satisfies (i)–(iii) locally, but lacks authoritative persistence over the objects it holds; it is a cache, not a repository, and fails both A and D. Therefore C does not entail A.

Conversely, does A entail C? The direction is analytic rather than constructive, and the paper states it as such: there is no coherent case of an authoritative holding environment without a preservation contract, retrieval mechanism, or purpose boundary, because authority over a holding is authority to preserve it, to make it retrievable, and to bound what it holds. A thing that is authoritative over a holding but has no preservation, retrieval, or boundary is not a weaker repository; it is not a repository at all — the phrase "authoritative holding environment" has no referent under those conditions. So A does not entail C either, in the sense that A and C are independently necessary for the conjunction to be satisfied: remove C and A is no longer coherently instantiated, which is exactly the independence the conjunction requires. The two cores are independent in both directions — the first direction constructively, the second analytically.

The same independence holds for B and D against each other and against A and C: a folder (B only) is not a repository; a mirror (D absent) is not a repository; a bare container (A only) is not a repository. Each conjunct can be removed without the remaining three yielding a repository, and each removal yields a recognized near-repository kind. The four conditions are therefore individually necessary and jointly sufficient. (Resolved; a reader can re-walk the argument.)

On disjointness. The partition is asserted at the level of primary function, not at the level of every possible metadata element. An element that serves both descriptive and provenance functions (common in PREMIS) is classified by its primary function, with the secondary function noted. The "exactly one" clause in the membership rule is therefore a claim about primary-function classification and is inferred at edge cases. This is a stated limitation of the taxonomy, not a defect in its statement. A reader who requires a fully disjoint partition at the element level should treat the taxonomy as a faceted classification (Ranganathan-style) rather than a partition, and the downstream argument is unaffected.

9. Closure

9.1 Novelty boundary

The invariant is component-novel, not component-invented. Its components are public: the senses are attested (OED; Lewis & Short; FEW); the specifications are published (Git; Maven; OCI; Evans; ISO 16363; OAI-PMH); the four-condition decomposition is a standard structural move in the analysis of institutional and informational systems. The synthesis — that these are re-instantiations of one invariant under one lens, closed by one criterion — is the contribution. No component is claimed as new. If the same synthesis is found in a prior publication, this paper's claim to synthesis-novelty fails and it becomes a restatement (F4, §9.3).

9.2 Resolved points

The paper resolves in place the following points, each of which is a claim that a careful reader could otherwise press: (1) the OED sense-mapping is cited to specific sense numbers; (2) the T-inventory is stated as an admission decision, with sources for each T; (3) the S3 core profile is argued (§3); (4) the §5.3 collapse question is argued, not asserted, with the A-without-C direction flagged as analytic; (5) the metadata taxonomy's disjointness is qualified at edge cases (§6); (6) the TUF specification version is cited (§7); (7) the DDD Repository-vs-DAO distinction is cited to Evans and Fowler (§4). Count: 7.

9.3 Falsification conditions

· F1 (diachronic). An attested sense of repository in a standard etymological source that satisfies no core. None known.
· F2 (synchrony). A technical specification that fails Core B (no apparatus/content separation) yet is universally called a repository by its community of practice, without metaphor. None known.
· F3 (structural). A domain in which apparatus/content separation is provably absent, yet the thing functions functionally as a repository and is treated as one by its users. None known.
· F4 (meta). A prior publication that states the same synthesis with a novelty claim. None known to the author.

If any of F1–F4 is met, the corresponding section is wrong and the paper must be revised. The falsifiers are stated so that a critic can run them; they are not defended here.

10. Conclusion

Repository names a functional invariant instantiated across eleven attested senses and eight technical specifications. The invariant is the conjunction of an authoritative organized holding environment (A), apparatus/content separation (B), a preservation-retrieval-boundary contract (C), and server-of-record authority (D). Each conjunct is necessary; the four are jointly sufficient; the proof is carried in §5.3. The paper has stated its novelty boundary (§9.1), its resolved points (§9.2), and its falsification conditions (§9.3). It is offered as a contribution to terminology and to the analysis of informational and institutional systems, not as a discovery of a new thing.

THE CONSOLIDATED ARTIFACT

Part 1 of 7 — Synthesis §1–§7

1. What the thing is, in one sentence

A repository — in the paper's own invariant sense (A∧B∧C∧D) — whose holdings are reality-coupled non-fiction units, each unit an authored human–AI–digital-VM collaboration published under pseudonymity of persons only, instantiated as a single self-contained file readable in three registers, and admitted, verified, and versioned by the repository's apparatus rather than by trust.

That sentence is the convergence point. Everything below decomposes it. It introduces no axiom the paper does not already contain.

2. The reflexivity that makes it converge

The blueprint is not a new theory beside the paper. It is the paper's invariant applied to itself. The repository of reality-coupled units is itself a repository, and satisfies the same four conditions:

Core Paper's condition How the blueprint satisfies it
A Authoritative, organized holding environment; persists over version; mediates access by internal logic Holds units; access mediated by register router and manifest
B Apparatus separated from raw content Apparatus = manifest, provenance records, falsifier suite, admission rules. Content = the units. Neither stored inside the other
C Preservation + retrieval + boundary Preservation = versioned units, immutable IDs. Retrieval = hash-addressable register routing. Boundary = admission rule
D Server-of-record, not a derived copy The repository is the authoritative record of the collaboration. A mirror is not it

This reflexivity is the frictionless resolution: the blueprint has no separate axioms. It is A∧B∧C∧D instantiated at one level up.

3. The three layers (collapsed from four)

The thread proposed four layers at different points. Collapsed, there are exactly three — the invariant-preserving count.

Layer 1 — The Unit. One self-contained file. Three registers (Plain / Paper / Machine), a capability-delta statement, and a claim-addressed provenance block. This is the content in B's sense.

Layer 2 — The Record. Per-unit provenance and pseudonymity record: stable pseudonymous identities, assertion/verification chain, falsifier results, version. This is apparatus. Lives outside the unit, keyed to the unit's immutable ID.

Layer 3 — The Repository. Manifest, admission rule, falsifier runner, version store, discovery surface. Also apparatus. This is what makes units a knowledge base rather than a pile of files.

Reader shell = presentation of Layer 1. Provenance spine = Layer 2 projected into Layer 1. Validation = Layer 3 acting on Layer 1 via Layer 2. The four-layer version was a projection artifact; three is correct and closed.

4. The forks, resolved

Each decided, not offered, with the one-line reason.

Fork Resolution Reason

5. The membership rules — eight conditions, each testable

A unit enters the repository iff all hold:

1. Invariant — holdings satisfy A ∧ B ∧ C ∧ D.
2. Registers — all three registers present; each section exists in all three; landing page routes by reader type.
3. Provenance — every assertion has ID, asserted_by (pseudonymous), verified_by (role-VM), status (resolved / exposable / inferred), and where applicable a falsifier.
4. Reality-coupling — no non-person entity fictionalized; every empirical claim has a real-world referent or is flagged inferred.
5. Pseudonymity — persons appear only under stable pseudonymous IDs that resolve to contributors without revealing them; resolution held by the repository, not the unit.
6. Capability delta — per section, what a reader can do after that they could not before.
7. Closure — every enumeration terminates by explicit count and stated membership rule.
8. Falsifiability — the unit states its own falsification conditions, runnable by the repository's falsifier suite.

Count: 8. A unit failing any one is not admitted. This is the paper's closure discipline applied to "unit" — the same move at one level up.

6. The Record — Layer 2, specified

The one genuinely new artifact. Per assertion:

```
claim:
  id: C-<section>-<ordinal>
  text: <the assertion>
  asserted_by: <pseudonym>          # human | author-VM
  verified_by: [<pseudonym>, ...]   # verifier-VM | adversary-VM | human
  real_world_referent: <citation | observation | derivation | null>
  status: resolved | exposable | inferred
  falsifier: <F-id | null>
  register_anchors: {plain, paper, machine, provenance}
```

The fleet, closed at four roles:

Role Function Cannot
author-VM Holds collaboration state, drafts claims Verify its own claims
verifier-VM Checks claims against real-world referents Assert new claims
adversary-VM Attempts to falsify every claim before publication Pass a claim it did not attack
archivist-VM Maintains provenance DAG, version history, pseudonym resolution Alter claim content

Count: 4. Separation of powers is structural, not procedural. Reality-coupling is enforced by the adversary, not trusted from the author.

Pseudonymity is resolved at the repository, not the unit. A pseudonym is a stable identifier that resolves to a contributor only through the repository's authority. The unit carries the pseudonym; the repository carries the resolution. This is Core B applied to authorship: the identity apparatus is separate from the authored content, and neither the unit nor a reader can collapse one into the other.

7. What "programmable" and "objective" resolve to

· Programmable — the unit schema is a closed record; the instantiation contract is machine-readable; the validation layer executes. A blueprint that produces a reader, a verification surface, and a repository entry from a unit is programmable. This one does.
· Objective — admission is by closure (eight conditions, counted) and by falsification (F1–F4 + unit-specific). A unit that cannot be falsified is not admitted. Objectivity is the admission criterion, not a claim about the author.

This is the honest boundary of the format, and it is named as such in Part 3.

Part 3 of 7 — Skill-verification layer

How skills are verified in reality

Capability-delta measurement is not a mystery. Every serious skill domain already solves it. The blueprint does not need to invent a method. It needs to adopt the methods that already work and name them as the measurement layer.

1. The general form: performance, not self-report

Every verified skill domain measures the same thing: can the person produce output that meets an external standard, without the scaffold they had before? Not "do they say they learned it." Not "do they feel capable." Output under observation, against a criterion, by an assessor who is not the learner.

That is the invariant of skill verification. The domains differ only in what output, what criterion, and who assesses.

2. The methods that already exist, by domain

Domain Output produced Criterion Assessor What it proves
Trades / vocational Physical artifact or completed job Code standard + inspection Licensed examiner Skill transfers to real materials
Medicine Procedure or diagnosis Checklist (OSATS), patient outcome Attending physician Competence under real conditions
Aviation Flight maneuver or emergency procedure Practical test standards (PTS) Designated examiner Competence under stress
Music Performance of a set piece Graded exam (ABRSM, Trinity) External examiner Technique + interpretation
Language Spoken/written production CEFR can-do descriptors Certified rater Communicative ability
Software Working code, passing tests, shipped feature Test suite, code review, production metrics Peer reviewer + CI Code does what it claims
Mathematics Proof or solution Correctness proof, peer review Mathematician Derivation is valid
Craft (writing, design) Portfolio piece Rubric + expert judgment Editor / critic Taste and execution
Safety-critical ops Drill performance Pass/fail checklist Certified evaluator Procedure is internalized
Science Replication of an experiment Result matches published finding Independent lab The claim is real

Count: 10 domains. Every one measures output production against an external criterion by a non-self assessor. That is the invariant.

3. What makes a capability claim verified rather than asserted

Across all ten domains, four conditions recur:

1. An observable output — something the reader produces that can be inspected.
2. An external criterion — a standard not set by the learner.
3. A non-self assessor — someone or something that is not the person claiming the capability.
4. A before/after comparison — the output is produced without the scaffold the reader had before.

A capability claim that lacks any one is a self-report, not a verification.

4. Where verification doesn't exist — and the three tiers

Some capabilities have no external verification method in current practice: judgment/taste, long-horizon capabilities, meta-capabilities. For these, the honest move is not to claim verification. The blueprint requires every capability delta to declare its tier:

· Tier 1 — Verifiable now: output + criterion + assessor + before/after all exist. The repository's falsifier suite can run it.
· Tier 2 — Verifiable with effort: the method exists but requires a human assessor or longer observation. The unit states the method; the repository records Tier 2.
· Tier 3 — Not currently verifiable: the unit states the capability, states Tier 3, and does not claim verification. Honest and not a defect — it is a boundary.

The blueprint becomes objective not by claiming everything is verifiable, but by requiring every capability claim to declare its tier.

5. The one thing that remains genuinely open

Whether a Tier 1 test actually measures the capability it claims to measure — psychometric validity. A coding test can be passed by memorization; a weld can pass inspection and fail in service; a CEFR rating can be gamed. Test validity is a research program in every domain, and no format can close it.

What the format can do:

· Every Tier 1 test must state what it measures and what it does not measure.
· The repository records known failure modes of each test.
· A unit whose Tier 1 test has a known failure mode is still admitted, but the failure mode is published alongside the capability claim.

That is the honest boundary: the format can require transparency about test validity. It cannot supply validity.

6. The capability_delta field, specified

```
capability_delta:
  - id: CD-<section>-<ordinal>
    statement: <what the reader can do after>
    tier: 1 | 2 | 3
    output: <what the reader produces>
    criterion: <the external standard>
    assessor: <who or what assesses>
    scaffold_removed: <what the reader no longer needs>
    test: <runnable test, Tier 1 only>
    measures: <what the test measures>
    does_not_measure: <known failure modes>
```

Count: 9 subfields for a Tier 1 capability. Tier 2 drops test and adds method. Tier 3 drops test, criterion, assessor and states why_not_verifiable.

The capability_delta field is no longer a gesture. It is a closed record, closed by the same discipline as everything else in the blueprint.

7. The verification predicate, formalized

```
verified(cd) ≡
    produces(reader, output_artifact(cd))
  ∧ assesses(assessor(cd), output_artifact(cd))
  ∧ criterion(cd) ∉ set_by(reader)
  ∧ ¬could_have_produced_before(reader, output_artifact(cd))
```

The four failure modes:

Predicate Failure mode Diagnosis
produces fails Self-report Testimonial only, no artifact
assessor = reader Self-assessment Graded by the reader
criterion set by reader Moving goalposts Criteria chosen post hoc
could_have_produced_before Pre-existing capability Artifact produced by prior skill

8. The answer, stated plainly

Skills are verified in reality by output production against an external criterion, assessed by a non-self assessor, with the scaffold removed, compared before and after. Ten domains already do this. The blueprint adopts it, requires it, and tier-labels the claims that can't meet it.

What the blueprint adds is the requirement that the production be stated, the criterion be external, the assessor be named, the scaffold be removed, and the tier be honest. That is what turns "this book gives you a skill" from a claim into a record.

```typescript
export type AdmissionFailure =
  | "A1_invariant_not_satisfied"
  | "A2_registers_incomplete"
  | "A3_provenance_incomplete"
  | "A4_reality_not_coupled"
  | "A5_pseudonymity_violated"
  | "A6_capability_delta_invalid"
  | "A7_closure_not_counted"
  | "A8_falsifiers_missing_or_unrunnable"
  | "A9_capability_delta_tier_or_status_missing";

export function admitted(
  u: Unit
): { ok: true } | { ok: false; failures: AdmissionFailure[] } {
  const failures: AdmissionFailure[] = [];

  // A1 — invariant instantiated
  if (!invariantHolds(u.invariant)) {
    failures.push("A1_invariant_not_satisfied");
  }

  // A2 — registers complete (all four)
  const regs = new Set(u.registers);
  if (regs.size !== 4 || !REGISTERS.every((r) => regs.has(r))) {
    failures.push("A2_registers_incomplete");
  }

  // A3 — provenance: every claim is complete AND separation of powers holds
  // AND referent-or-inferred. This is the proper A3 — not a stub.
  for (const c of u.claims) {
    const complete =
      c.id.length > 0 &&
      c.text.length > 0 &&
      c.assertedBy.length > 0 &&
      c.assertedRole !== undefined &&
      c.status !== undefined;

    if (!complete) {
      failures.push("A3_provenance_incomplete");
      break;
    }

    if (!separationOfPowersHolds(c)) {
      failures.push("A3_provenance_incomplete");
      break;
    }

    if (c.referent.kind === "none" && c.status !== "inferred") {
      failures.push("A3_provenance_incomplete");
      break;
    }
  }

  // A4 — reality-coupling: no fictionalized non-person
  for (const c of u.claims) {
    if (c.referent.kind === "none" && c.status !== "inferred") {
      failures.push("A4_reality_not_coupled");
      break;
    }
  }
  if (u.pseudonymity.realNonPersons !== true) {
    failures.push("A4_reality_not_coupled");
  }

  // A5 — pseudonymity declaration
  if (
    u.pseudonymity.pseudonymousPersons.length === 0 &&
    u.claims.length > 0
  ) {
    failures.push("A5_pseudonymity_violated");
  }

  // A6 — capability delta: at least one, all well-formed
  if (u.capabilityDeltas.length === 0) {
    failures.push("A6_capability_delta_invalid");
  } else {
    for (const d of u.capabilityDeltas) {
      if (!capabilityIsWellFormed(d)) {
        failures.push("A6_capability_delta_invalid");
        break;
      }
    }
  }

  // A7 — closure: declared counts match actual lengths.
  // This is the proper A7 — not a stub.
  if (
    u.closure.claimCount !== u.claims.length ||
    u.closure.deltaCount !== u.capabilityDeltas.length ||
    u.closure.falsifierCount !== u.falsifiers.length
  ) {
    failures.push("A7_closure_not_counted");
  }

  // A8 — falsifiers stated and runnable (present)
  if (u.falsifiers.length < 4) {
    failures.push("A8_falsifiers_missing_or_unrunnable");
  }
  if (!u.falsifiers.every((f) => typeof f === "string" && f.length > 0)) {
    failures.push("A8_falsifiers_missing_or_unrunnable");
  }

  // A9 — every capability delta is tiered
  for (const d of u.capabilityDeltas) {
    if (!(d.tier === 1 || d.tier === 2 || d.tier === 3)) {
      failures.push("A9_capability_delta_tier_or_status_missing");
      break;
    }
  }

  return failures.length === 0
    ? { ok: true }
    : { ok: false, failures };
}

// ============================================================
// VALIDATE — the falsifier suite (3 conjuncts)
// ============================================================

export function validate(u: Unit, repo: Repository): boolean {
  // 1. the repository's validation record does not report a fired falsifier
  const rec = repo.validation.find((v) => v.unitId === u.id);
  if (rec && !rec.passed) return false;

  // 2. every capability delta has a terminal status, and none is failed
  for (const d of u.capabilityDeltas) {
    const terminal =
      d.status === "verified" ||
      d.status === "inferred" ||
      d.status === "failed" ||
      d.status === "not_attempted";
    if (!terminal) return false;
    if (d.status === "failed") return false;
  }

  // 3. every verified delta has a matching registry record with a non-self assessor
  for (const d of u.capabilityDeltas) {
    if (d.status === "verified") {
      const r = repo.registry.find((v) => v.deltaId === d.id);
      if (!r || r.result !== "pass") return false;
      if (d.assessor.kind === "author-VM") return false;
    }
  }

  return true;
}

// ============================================================
// ENTRY — Ω := μX. { u ∈ U* | admitted(u) ∧ validate(u, X) }
// ============================================================

export function omega(
  candidates: readonly Unit[],
  repo: Repository
): readonly Unit[] {
  const out: Unit[] = [];
  for (const u of candidates) {
    const a = admitted(u);
    if (a.ok && validate(u, repo)) out.push(u);
  }
  return out;
}
```

```typescript
export function runTests(): {
  passed: number;
  failed: number;
  failures: string[];
} {
  let passed = 0;
  let failed = 0;
  const failures: string[] = [];

  for (const [name, test] of Object.entries(TESTS)) {
    let result: boolean;
    try {
      result = test();
    } catch (e) {
      result = false;
      failures.push(`${name} (threw: ${(e as Error).message})`);
      failed++;
      continue;
    }
    if (result) {
      passed++;
    } else {
      failed++;
      failures.push(name);
    }
  }

  return { passed, failed, failures };
}
```

```typescript
import { invariantHolds } from "./invariant.js";

import { Unit } from "./unit.js";

export interface Repository {
  readonly manifest: readonly string[];
  readonly validation: readonly { unitId: string; passed: boolean }[];
  readonly registry: readonly { deltaId: string; assessor: string; result: "pass" | "fail"; }[];
}

export type AdmissionFailure =
  | "A1_invariant_not_satisfied"
  | "A2_registers_incomplete"
  | "A3_provenance_incomplete"
  | "A4_reality_not_coupled"
  | "A5_pseudonymity_violated"
  | "A6_capability_delta_invalid"
  | "A7_closure_not_counted"
  | "A8_falsifiers_missing_or_unrunnable"
  | "A9_capability_delta_tier_or_status_missing";

export function admitted(u: Unit): { ok: true } | { ok: false; failures: AdmissionFailure[] } {
  const failures: AdmissionFailure[] = [];

  if (!invariantHolds(u.invariant)) failures.push("A1_invariant_not_satisfied");

  const regs = new Set(u.registers);
  if (regs.size !== 4 || !REGISTERS.every((r) => regs.has(r))) failures.push("A2_registers_incomplete");

  for (const c of u.claims) {
    if (c.referent.kind === "none" && c.status !== "inferred") failures.push("A3_provenance_incomplete");
    if (!separationOfPowersHolds(c)) failures.push("A3_provenance_incomplete");
  }

  if (u.claims.some(c => c.referent.kind === "none" && c.status !== "inferred")) failures.push("A4_reality_not_coupled");
  if (u.pseudonymity.realNonPersons !== true) failures.push("A4_reality_not_coupled");

  if (u.pseudonymity.pseudonymousPersons.length === 0 && u.claims.length > 0) failures.push("A5_pseudonymity_violated");

  if (u.capabilityDeltas.length === 0 || !u.capabilityDeltas.every(capabilityIsWellFormed)) failures.push("A6_capability_delta_invalid");

  if (u.closure.claimCount !== u.claims.length || u.closure.deltaCount !== u.capabilityDeltas.length || u.closure.falsifierCount !== u.falsifiers.length) failures.push("A7_closure_not_counted");

  if (u.falsifiers.length < 4 || !u.falsifiers.every(f => typeof f === "string" && f.length > 0)) failures.push("A8_falsifiers_missing_or_unrunnable");

  if (!u.capabilityDeltas.every(d => d.tier === 1 || d.tier === 2 || d.tier === 3)) failures.push("A9_capability_delta_tier_or_status_missing");

  return failures.length === 0 ? { ok: true } : { ok: false, failures: Array.from(new Set(failures)) };
}

export function validate(u: Unit, repo: Repository): boolean {
  const rec = repo.validation.find((v) => v.unitId === u.id);
  if (rec && !rec.passed) return false;

  for (const d of u.capabilityDeltas) {
    if (d.status === "failed") return false;
    if (d.status === "verified") {
      const r = repo.registry.find((v) => v.deltaId === d.id);
      if (!r || r.result !== "pass") return false;
    }
  }
  return true;
}
```

# Darkith Omega Homekeeper

This is the executable specification and codebase for the **Darkith Omega Homekeeper** (formerly `/unit-repository`). It enforces the four-core invariant (A∧B∧C∧D) on reality-coupled units.

- **`src/record.ts`**: Layer 2. Claim records, capability deltas, and the fleet separation-of-powers.

- **`src/omega.ts`**: The fixed-point calculation (`omega()`).
- **`src/reader.ts`**: The single-file HTML generator.
- **`src/tests.ts`**: The test runner (A1–A9, separation of powers, omega).

## How to Run the Tests

1. Ensure Node.js is installed.
2. Navigate to `/darkith-omega-homekeeper`.

   ```bash
   npm install
   npm test
```
